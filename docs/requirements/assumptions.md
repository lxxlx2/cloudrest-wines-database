# Explicit Modelling Assumptions

These assumptions resolve ambiguity without contradicting the case. They must be reviewed by the team/tutor and placed beneath the final ER diagram.

| Design area | Assumption | Reason |
|---|---|---|
| Employee names | Names are split into first and last name for all employees | The case says employee name but does not prescribe structure; splitting supports contact and reporting use |
| Concurrent roles | The first implementation allows one active role period per employee | The case describes role changes but does not explicitly require concurrent roles; this can be relaxed if tutor confirms concurrent appointments |
| Supervisor history | An employee has no more than one supervisor at any instant | Explicit case requirement |
| Employment classification | Full/part-time, permanent/casual and ongoing/seasonal are independent dimensions | Prevents a seasonal casual from being misclassified as a third legal employment type |
| Employee/customer addresses | Physical and postal histories may coexist, but periods of the same address type for one owner may not overlap | Allows correspondence and physical addresses while preserving an unambiguous address of each type at a point in time |
| Supplier contact history | A supplier may hold a current physical address and an optional current postal address at the same time; histories must not overlap within the same address type. Multiple phone numbers may coexist, but only one phone may be primary for an overlapping period | Matches the case requirement for physical address plus optional postal correspondence while retaining address/phone history |
| Owners | Christine is represented as an employee/owner role so supervisor FKs remain enforceable | Supervisors report to Christine and the model needs an identifiable parent record |
| Picking pack | Cross-row pack rules are checked by `validatePickingPackRules()` before operational use: at least four current members, current casual-seasonal Picker roles, one pack per current picker, an active Grape Farmer supervisor and matching current supervision | A row trigger would make it impossible to build a new pack incrementally, while an explicit validation procedure gives the deferred rule an executable database control |
| Vineyard manager | The current manager must have an active Grape Farmer role, the address must be physical and a manager can manage at most one vineyard. A future extension could add dated vineyard-management history | The case requires a grape-farmer manager and one-vineyard-per-manager rule but does not explicitly require manager history |
| Wine recipe | Composition rows may be staged incrementally, but `validateWineComposition()` and wine-product triggers require at least one composition row totalling exactly 100% before a saleable product is created | Preserves staged recipe entry while enforcing a complete recipe at the release-to-product boundary |
| Product identity | Wine, bottle type and case quantity uniquely define a product | Directly follows the case definition of product |
| Shipment | Each customer order has at most one shipment, must contain at least one order line before shipment and the shipment retains its physical address ID | The case prohibits back orders and requires a single shipment to the current physical address |
| Customer subtypes | Parent customer rows may be staged before the subtype row is inserted; subtype triggers prevent mismatched/dual subtypes and `validateCustomerSubtype()` prevents an incomplete parent from placing an order | Supports staged loading while requiring exactly one matching subtype before the customer transacts |
| Receipt lines | A received bottle type must exist on the purchase order associated with the receipt; cumulative over-delivery is not automatically rejected | The case links receipts to supplier orders but does not state how over-delivery should be handled |
| Product price history | Price validity periods for the same product must not overlap and use DATE granularity | The case requires dated price history with 24-hour price changes |
| HR incident rate | The selected management KPI counts every safety event recorded in `incident` once per operational area, including near misses; `reportableFlag` is retained separately for statutory/reportability analysis | Matches Query 2 and avoids double-counting a multi-person incident |
| Serious near miss | HIGH or CRITICAL severity may have zero lost hours | Severity and lost time measure different concepts; the case does not require positive lost time |
| Labour hours | `regularHours + overtimeHours` in shift assignments is the exposure denominator | Required to calculate incidents per 1,000 labour hours |
| Shift time | The current course implementation models same-day shifts and treats 16 regular / 18 total hours as defensive data-quality bounds, not as case-stated employment policy | The schema uses TIME values without a next-day flag and needs a bounded test-data domain; tutor confirmation may justify relaxing this |
| Wellbeing privacy | Detailed notes are restricted; decision-support queries expose only concern counts and actions | Applies data minimisation to sensitive HR information |
